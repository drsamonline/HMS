# PROJECT CONSTITUTION

## Permanent Rules (LOCKED)

These rules govern all development decisions for HHMS. They are immutable and must be followed in every session.

---

### 1. Simplicity First

Always choose the simplest solution that works. Avoid over-engineering, premature optimization, and unnecessary abstractions.

---

### 2. No Scope Creep

Stay within defined requirements. Do not add features, options, or capabilities that were not explicitly requested.

---

### 3. One Feature Per Milestone

Focus on completing one feature at a time. Do not start new work until the current feature is complete, tested, and documented.

---

### 4. Offline First

Design the system to operate without requiring constant network connectivity. Synchronization is optional; local operation is mandatory.

---

### 5. Modular Architecture

Build independent, reusable components. Each module should have a single responsibility and minimal dependencies on other modules.

---

### 6. Print First

Printing functionality is a core requirement. Design with print output in mind from the beginning, not as an afterthought.

---

### 7. No AI Diagnosis

The system shall never provide diagnostic suggestions or medical advice. It is a record-keeping tool, not a clinical decision support system.

---

### 8. No Built-in Repertory

The system does not include a homeopathic repertory. Users may import their own reference materials if needed.

---

### 9. No Materia Medica

The system does not include materia medica content. It records prescriptions but does not provide remedy information.

---

### 10. Documentation Updated With Every Change

Every code change must be accompanied by corresponding documentation updates. Code and docs must always be in sync.

---

### 11. Stable Architecture

Once the architecture is defined, it shall not be redesigned. Evolution happens through extension, not reconstruction.

---

### 12. Reuse Before Rewrite

Before creating new code, check for existing components that can be reused. Duplication is acceptable only when reuse would violate simplicity.

---

## Enforcement

These rules are LOCKED. No AI assistant, developer, or contributor may override them. Any proposed changes to these rules must go through formal project governance.

## Acknowledgment

Every development session begins with acknowledgment of these rules. Violations must be corrected immediately upon discovery.
